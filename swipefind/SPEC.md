# swipefind 规范 · 滚动手势的有效性与吸收判定

**版本** 0.1.0 · **日期** 2026-10-27 · **License** Apache-2.0
**测试环境** AVD `avd-api35`（Android 15 / Google APIs / arm64-v8a），emulator-5554

---

## 0. 这个问题是什么

agent 要滚动列表找一个目标。它发出 `adb shell input swipe`，
命令**返回成功、退出码 0**。然后：

- 界面没动 —— 而 agent 以为动了
- 或者界面动了，但**输入框里多出了几个字** —— 而 agent 以为自己在滚动

两种情况都没有任何异常信号。

---

## 1. 真机证据

### 1.1 ★ 距离非单调：太长也会静默失败

固定时长 250ms，只改距离（AVD Android 15，设置列表，垂直滑动）：

| 距离 | 新增 | 消失 | 结果 |
|---|---|---|---|
| 100px | 0 | 0 | ❌ 无效 |
| 300px | 0 | 1 | ❌ 无效 |
| 600px | 2 | 1 | ✅ 有效 |
| 900px | 2 | 3 | ✅ 有效 |
| **1200px** | **0** | **0** | **❌ 无效** |
| **1500px** | **0** | **0** | **❌ 无效** |

**不是"越长越好"。有一个甜点区，超过它同样静默失败。**

本环境实测甜点区约 500–1100px（250ms）。

### 1.2 ★★ 键盘区起滑会被吸收，往输入框里写字

设置页搜索，输入 `net`，键盘弹起。四种手势，全部复现：

| 手势 | 字段变化 |
|---|---|
| 键盘区垂直上滑 (540,2000)→(540,1000) 400ms | `net` → **`net by`** |
| 键盘区斜滑 (700,2100)→(380,1200) 400ms | `net` → **`net be`** |
| 键盘区短滑 (540,1900)→(540,1600) 400ms | `net` → **`net gt`** |
| **对照 · App 区滑动** (540,1400)→(540,400) | `net` → `net`（未变 ✅） |

**一次滚动手势，静默往输入框写入 2–3 个字符。**

这是 `blindspot` 的 tap 发现的手势版，但更糟：
tap 写一个字符（`net` → `netv`），**swipe 写多个**。

### 1.3 终止信号干净

连续下滚，记录每步新增/消失：

| 步 | 新增 | 消失 |
|---|---|---|
| 1 | 9 | 6 |
| 2 | **0** | **0** |

`new == 0 and gone == 0` 且内容哈希不变 → 到底。

### 1.4 滚动可恢复，且到顶后幂等

- 下滚 3 步 + 上滚 3 步 → 恢复 **18/22** 初始元素（81.8%）
- 到顶后再上滑 10 步 → 内容完全不变（**幂等**）
- `input keyevent KEYCODE_PAGE_UP` 与 `input scroll` 与 swipe 等效

## 2. ★ 一个方法论坑：`reset_home()` 不是可靠复位

实验 1 和实验 3 用 `am start -a android.settings.SETTINGS` + `KEYCODE_BACK`
复位，得出两个**错误**结论：

- 实验 1："200ms 以下完全无效"（阈值假象）
- 实验 3："滚过头不可恢复，restored = 0/6"

实验 4 改用 **HOME 键 + 重新进设置**复位后：

- 200ms 其实有效（新增 4）
- 下滚 3 + 上滚 3 恢复 18/22

**根因**：`am start` 到已在前的 Activity 不会重置滚动位置；
`KEYCODE_BACK` 在某些状态下回到的是启动器而非列表顶部。

> **C5**：任何依赖"回到初始状态"的实验或 agent 循环，
> 必须 用可验证的复位（如 HOME 键），不得 假定
> `am start` + `BACK` 能复位滚动位置。
> **复位本身也要有判据**——否则装置的失败会被当成被测对象的失败。

## 3. 判定

### 3.1 手势长度

```
dist = hypot(x2-x1, y2-y1)
short     < 400px
sweet     500..1100px      ← 本环境实测有效区
too_long  > 1100px
```

**非单调。** 短了不动，太长也不动。

### 3.2 键盘吸收

```
absorbed = 起点在 IME 矩形内
```

> **C1**：吸收判据 必须 是**起点**在键盘内，
> 不得 用"路径与键盘相交"。

实测依据：起点在键盘内三种手势全被吸收；
起点在 App 区、终点穿进键盘的手势**不**写入。

### 3.3 路径相交

判定"路径是否穿过键盘"必须 用**线段-矩形相交**，
不得 用端点包围盒。

> **C2**：垂直滑动的路径包围盒是**零宽矩形**，与任何矩形的
> 重叠面积恒为 0。用包围盒判定会让"路径穿过键盘"永远 False——
> 这是一个静默失效的判据。

### 3.4 滚动终止

```
exhausted = 最近 window 步的 new == 0 且 gone == 0
```

> **C3**：`window` 必须 >= 2。一步为 0 可能只是渲染延迟。
> 本环境实测：探针看到第一个 0 步就停了，所以真机数据里
> 只有一个 0 步——**规范比观测更保守，这是刻意的**。

## 4. 参考实现

```python
from swipefind import (absorbed_by_keyboard, gesture_length,
                       is_exhausted, likely_effective, recovery_ratio)

# 这个手势会滚吗？
likely_effective(600, 250)     # 'likely'
likely_effective(1500, 250)    # 'unlikely'  ← 太长也不行

# 这个手势会被键盘吸收吗？
absorbed_by_keyboard(540, 2000, 540, 1000, ime)["absorbed"]   # True
absorbed_by_keyboard(540, 1400, 540, 400, ime)["absorbed"]    # False

# 滚到底了吗？
is_exhausted([{"new": 9, "gone": 6}, {"new": 0, "gone": 0},
              {"new": 0, "gone": 0}])                          # True
```

## 5. 对 agent 的直接含义

1. **滑动前先查吸收**。键盘可能弹着（刚写过文本？刚点过输入框？）。
   起点在键盘区的手势一律不要发。
2. **滑动距离取甜点区**，不要贪心。本环境 600–900px @ 250ms。
3. **滑完必须验证**。`new + gone == 0` 且内容哈希不变 →
   要么到底了，要么手势失败了。**这两种情况必须区分**：
   再发一次同样手势，若仍无变化，才是到底。
4. **复位用 HOME 键**，并且验证真的复位了。

## 6. 一致性条件

| # | 条件 |
|---|---|
| C1 | 吸收判据 必须 是起点在键盘内，不得 用路径相交 |
| C2 | 路径相交 必须 用线段-矩形相交，不得 用端点包围盒 |
| C3 | `is_exhausted` 的 window 必须 >= 2 |
| C4 | `parse_bounds` 必须 正确处理 `[x1,y1][x2,y2]` 内部逗号 |
| C5 | 复位 必须 可验证，不得 假定 `am start`+`BACK` 能复位滚动位置 |
| C6 | 手势长度分类 必须 非单调（存在 too_long），不得 实现成"越长越可能有效" |

---

## 7. 边界

1. **一台 AVD、一个列表、一个方向（垂直）、一个时长。**
   甜点区数值换设备/换方向需重跑 `tools/probe_threshold.py`。
2. **`likely_effective` 的 short/too_long 判据只在本环境实测过。**
   换设备必须重测，不得沿用数值。
3. **水平滚动、多指手势、`input roll`、`input draganddrop` 未测。**
4. **未测：`adjustResize` 下的滚动**（窗口会缩小、bounds 会变）。
5. **不处理"怎么把键盘收起来"**——`KEYCODE_BACK` 会同时触发返回逻辑。

## 8. 与其他库的关系

| 库 | 关系 |
|---|---|
| `blindspot` | blindspot 判"点下去命中谁"；swipefind 判"滑下去命中谁" |
| `imespec` | imespec 判"元素被挡了多少"；swipefind 判"手势会不会被挡" |
| `fieldstate` | ★ swipefind 的失败会**污染输入框**——正好落在 fieldstate 的管界 |
| `agentloop` | agentloop S2 的"11/14 步无效上滑"，其机制在本库有解 |
| `devapi` | `/v1/act` 的 swipe 端点应先过 `absorbed_by_keyboard` |
