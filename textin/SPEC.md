## 2. 为什么需要这份规范

GUI agent 迟早要填表单、搜关键字。这件事看起来是"一条 adb 命令"，
实测有 **19 类输入里只有 4 类能完整落进输入框**（见 §4）。

`stepfun-ai/gelab-zero` 的代码把这个信号写得很清楚——
外部项目 gelab-zero 的 copilot_front_end/mobile_action_helper.py（非本仓库路径）：

```python
elif action['action_type'] == "Type":
    text = action['args']['text']
    # adb_command += f" shell input text '{text}'"          ← 注释掉
    # adb shell app_process -Djava.class.path=/data/local/tmp/yadb ...
    ...
    adb_command += f' shell app_process -Djava.class.path=/data/local/tmp/yadb /data/local/tmp com.ysbing.yadb.Main -keyboard "{text}"'
```

**它不用 `input text`，改用 yadb**：往 `/data/local/tmp` 推 jar、
跑 `app_process` 起一个 Java 进程、走输入法通道。
代价是要在设备上留文件、起进程，且**要求键盘已经弹出**
（同文件上方专门判断了 `keyboard_exists`，不弹就先点一下输入框）。

而 `copilot_front_end/pu_frontend_executor.py:84-88` 还留着一段
**也注释掉的**手动转义残骸：

```python
#     value = ui_action.get("value", "")
#     value = value.replace(" ","_").replace("(", "\(").replace(")", "\)")...
```

注意第一个替换：**把空格换成下划线**。这不是"处理空格"，
这是"放弃空格"。两代实现都被注释掉，说明这个问题不好解。

## 3. 判定口径（本规范最重要的一条）

**不要假设空输入框的 `text` 属性是空字符串。**

实测：设置搜索框（`com.google.android.settings.intelligence`）空的时候：

```
text = "Search settings"        ← 这是提示文字（hint），不是内容
```

所以 `text == ""` 不能用来判断"字段是空的"。
按这个假设写校验，会把空字段判成有内容，也会把成功的输入判成失败。

**本规范采用三分判定**，拿输入前的回读当基线，只比较变化：

| 判定 | 条件 | 含义 |
|---|---|---|
| **干净** | `after == text` | 输入结果与原文完全一致 |
| **部分** | `after != before` 且 `text ⊆ after` | 有东西落进去了，但不全对 |
| **无变化** | `after == before` | 什么都没落（基线本身是 hint） |

`before` 的获取方式：清空后回读一次。清空的判据是**回读回到 `before`**，
不是回读变成 `""`——后者在这个字段上永远做不到。

## 4. 失败分类（真机取证，19 类）

设备：AVD `avd-api35`（Android 15 / Google APIs / arm64-v8a），emulator-5554。
测试方式：`subprocess.run([adb, "-s", dev, "shell", "input", "text", text])`
——**参数列表，不经本机 shell**，所以下面所有失败都来自**设备侧**那一层。

复现：`python tools/probe_input_text.py`（约 4 分钟，19 用例）

### 4.1 干净通过（4 / 19）

| 原文 | 回读 |
|---|---|
| `hello` | `hello` |
| `a#b` | `a#b` |
| `a*b?` | `a*b?` |
| `x` × 200 | `x` × 200 |

**读法**：长度不是问题（200 字符完整落地）；
`#` `*` `?` 这些 glob 字符也没事——因为 `input` 不是 shell 内建，
它们不经过 glob 展开。

### 4.2 空格被截断（1 / 19）——最隐蔽的一类

| 原文 | 回读 |
|---|---|
| `hello world` | `hello` |
| `a b%s` | `a` |
| ` pad ` | `pad` |

**静默截断**：`adb` 退出码 0，没有任何报错。
agent 以为输入了 "hello world"，实际只进去 "hello"。

这正是 gelab-zero 那段 `value.replace(" ","_")` 想绕过的东西。

### 4.3 非 ASCII 直接抛异常（2 / 19）——最明显的一类

| 原文 | adb 退出码 | stderr |
|---|---|---|
| `你好世界` | **255** | `Exception occurred while executing 'text': java.lang.NullPointerException` |
| `hi😀ok` | **255** | 同上 |

**这是好事**：它**响**。退出码 255 + 明确异常，agent 至少知道失败了。
比 4.2 的静默截断好处理得多。

### 4.4 设备侧 shell 解释元字符（8 / 19）——最危险的一类

| 原文 | 回读 | adb 退出码 | stderr |
|---|---|---|---|
| `a;b` | `a` | 127 | `/system/bin/sh: b: inaccessible or not found` |
| `` a`b`c `` | `ac` | 0 | `/system/bin/sh: b: inaccessible or not found` |
| `a$b` | `a` | 0 | — |
| `a\|b` | `a` | 127 | `/system/bin/sh: b: ...` |
| `a&b` | `a` | 127 | `/system/bin/sh: b: ...` |
| `a(b)c` | *无变化* | 1 | `/system/bin/sh: syntax error: unexpected '('` |
| `a'b` | *无变化* | 1 | `/system/bin/sh: no closing quote` |
| `a"b` | *无变化* | 1 | `/system/bin/sh: no closing quote` |

**关键点：即使本机用参数列表、完全不经本机 shell，设备侧仍然有一层 shell。**

`adb shell <cmd>` 在设备上等价于 `/system/bin/sh -c <cmd>`。
所以 `;` `` ` `` `$` `|` `&` `(` `'` `"` 全部被**设备侧 shell**解释：

- `;` `|` `&` → 命令分隔/管道/后台，`b` 被当成一条命令去找，找不到 → 127
- `` ` `` → **命令替换**：`a`b`c` 里的 `b` 被执行，剩下 `ac`
- `$` → 变量展开，`$b` 展开成空
- `(` → 子 shell，语法错误
- `'` `"` → 引号不闭合

**这一类的危险在于它可能不只是"输入错"**：
`` a`b`c `` 里的 `b` 是被**执行**的。如果 agent 要输入的文本里
含反引号，它在设备上跑了一条命令。这是**注入面**，不只是数据损坏。

### 4.5 转义符自身（2 / 19）

| 原文 | 回读 | 说明 |
|---|---|---|
| `a%s` | `a ` | `%s` 是 adb 自己的空格转义序列，被解开成一个空格 |
| `a\b` | `ab` | 反斜杠被吃掉 |

`%s` 这条是 adb 的**既有约定**（空格写成 `%s`），
所以它也反过来污染真正想输入 `%s` 的场景。

## 5. 汇总：19 类的失败画像

| 类 | 数量 | 特征 | 危险度 |
|---|---|---|---|
| 干净 | 4 | 完整落地 | — |
| 空格截断 | 3 | **退出码 0，静默** | 高（无声失败） |
| 非 ASCII | 2 | **退出码 255，有声** | 低（可检测） |
| shell 元字符 | 8 | 部分 127 / 部分 1，**且可能执行命令** | **最高（注入面）** |
| 转义符自身 | 2 | 退出码 0，静默 | 中 |

**只有 4/19 能完整落地。** 而"纯 ASCII 无空格无元字符"这个子集，
恰好是真实任务里最不常见的那种输入。

## 6. 可行替代路径

| 路径 | 能处理 | 代价 | 需 root？ |
|---|---|---|---|
| **空格转 `%s`** | 仅空格 | 与"想输入 %s"冲突 | 否 |
| **输入法通道**（yadb / `app_process`） | unicode + 空格 | 设备留 jar、起 Java 进程、**要求键盘已弹出** | 否 |
| **`am broadcast` / `service call`** | 依实现 | 需要目标 App 配合 | 否 |
| **剪贴板 + 粘贴** | 完整文本 | 需聚焦长按菜单，或 `input keyevent KEYCODE_PASTE`（API 24+ 但需 App 配合） | 否 |
| ** Accessibility 直接 `ACTION_SET_TEXT`** | **完整文本，含 unicode** | 需无障碍权限；本套件 uidref 已有无障碍读取，写入是同一把钥匙 | 否 |

**最后一条（无障碍 `ACTION_SET_TEXT`）已在本环境真机验证通过，19/19。**
真机对照见 §6.1；参考实现见 `refapp/`。

**为什么它全过**：文本作为 Bundle 的一个字段传给 `performAction`，
**不经过任何 shell**。`input text` 的 15 类失败里有 10 类根源就是
设备侧那层 `/system/bin/sh -c`——`;` `` ` `` `$` `|` `&` `(` `'` `"` 全部
被它解释，而 `%s`、反斜杠、空格是 adb 自己的转义层。
**绕开 shell，这两层问题一起消失。**

它的理由：

1. **它是唯一不需要在设备上留文件、起进程的路**
2. 文本作为 **Intent/Bundle 的一个字段**传递，不经过任何 shell
   → §4.4 的整个注入面消失
3. unicode、空格、元字符一律按字符串处理，无转义层
4. 权限模型清晰：`BIND_ACCESSIBILITY_SERVICE` 是公开权限，
   用户在系统设置里显式开启，随时可关

**它的代价**：需要无障碍权限。但这正是"agent 操作设备"这件事的
正常门槛——`uidref` 的读取侧已经在用同一把钥匙。

### 6.1 真机对照（AVD Android 15，19 用例）

同一段文本、同一个输入框、同一条清场流程，只换落笔的那一步：

## 7. 边界

1. **本规范的取证来自一台 AVD（Android 15 / Google APIs）。**
   ROM 之间 `input text` 的实现可能有差异。**换设备需重跑**
   `tools/probe_input_text.py`，不要假定数字一致。
   （结论的方向性——空格截断、非 ASCII 抛异常、元字符被 shell 解释——
   来自 `adb shell` 的通用实现，跨设备应成立；**精确计数**不应外推。）
2. **未测**：密码框（`password="true"`）的回读会被屏蔽，
   判定口径在那种字段上不适用。
3. **未测**：`input keyevent` 逐字符输入是否也有同类问题
   （它走的是另一条路，预期不受 shell 影响，但没验）。
4. **§6.1 的对照只覆盖"整段替换"语义**。未测：光标不在末尾时的行为、
   只读字段、以及 `ACTION_SET_TEXT` 与输入法联想状态的交互。

## 8. 一致性条件

| # | 条件 |
|---|---|
| C1 | 任何实现不得假设空输入框的 `text` 是空串（§3） |
| C2 | 判定必须使用三分法（干净/部分/无变化），不用二分法（§3） |
| C3 | 取证脚本必须在输入前验证 `focused == true`，未验证不出具结论 |
| C4 | 取证脚本必须在输入前验证字段已回到基线，未验证不出具结论 |
| C5 | 失败分类必须记录 adb 退出码与 stderr，只记回读不够 |
| C6 | 报告必须用**三类**区分失败：静默（退出码 0 且 stderr 空）/ 第三类（退出码 0 但 stderr 非空）/ 有声（退出码非 0） |
| C7 | 主张"绕开 shell 生效"时，必须同时证明**传输层**没被 shell 解释 |
| C7a | 传输层证明应该用 base64 等无元字符字符集，而非尝试转义 |

C3/C4 是本次开发用**四版错误**换来的，见 §9。

### 8.1 C6 为什么必须是三类而不是两类

原文只分「退出码 0 的静默失败」与「非 0 的有声失败」。数据里有一行
**两类都装不下**：

| 用例 | 输入 | 回读 | 退出码 | stderr |
|---|---|---|---|---|
| 反引号 | `` a`b`c `` | `ac` | **0** | `/system/bin/sh: b: inaccessible or not found` |

两个信号互相矛盾：

- 退出码 0 → 任何"看退出码"的调用方判为**成功**
- stderr 非空 → 它不是静默的
- 回读 `ac` ≠ 输入 → 它确实失败了

而**退出码是更常用的那个信号**。所以二分会把这一行归到"成功"，
`b` 被当成命令执行过这件事就彻底看不见。

→ 立为三类。第三类的定义：**退出码 0 但 stderr 非空**。
它比纯静默失败更值得单独一类——因为它有信号，只是信号在容易被忽略的那一侧。

`tests/test_evidence.py::test_c6_third_class_exists` 从已提交的
`data/probe_results.json` 复算这一类确实存在；若数据变动导致它消失，
该测试失败。

C3/C4 是本次开发用**四版错误**换来的，见 §9。

## 9. 开发记录：四版判定错误（本规范自己的教训）

| 版 | 错在哪 | 会得出的假结论 |
|---|---|---|
| v1 | 没聚焦输入框，按键全部落空 | "`input text` 100% 坏掉" |
| v2 | 清空不干净，回读恒为上一轮残留 | "所有输入都坏" |
| v3 | 不知道 hint 会被报进 `text`，空字段判为有内容 | 同上 |
| v4 | 判定口径改三分，但基线取自"启动时的 whatever 状态" | 部分对 |
| v5 | 基线恰好是脏的（上一轮残留 200 个 x），"删到等于基线"第一轮就通过 | 又全错 |
| v6 | **基线改为"删到不再变化"**，不依赖任何初始状态 | ✅ |

**共同点：四版里设备的行为一直是一样的，变的是我的装置。**

所以 SPEC 把 C3/C4 立成必须：**焦点没验证、字段没回到基线，就不出具结论。**
一条取证结论的可信度，取决于装置本身有没有被判据保护。
