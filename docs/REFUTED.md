# 反例集 · 7 条不可引用声明

> **本文的性质**：这是 `claimcheck` / `claimaudit` 的**反例教材**，不是成果清单。
> 每一条都是本项目自己犯过、后来被抓出来的错误。它们的价值不在「错」，
> 而在「**怎么被抓住的**」——那才是可复用的部分。
>
> 本文只做一件事：**把 7 条集中到一处，并写清每条的抓住机制**，
> 让人不需要翻各个目录就能看到全部反例。
>
> 与 `claimcheck/README.md`、`claimaudit/README.md` 的关系：
> 那两个库给出**规则**与**复算工具**，本文给出**实例**。
> 删掉本文，规则就没有可运行的用例。

> **⚠️ 本套件范围的说明**：本文共 7 条，其中 **3 条的资产在本套件内**
> （`capturetrap-nav` / `capturetrap-stale` / `swipefind-200ms`），
> 另 4 条（#3–#6）的资产是 `agentloop` / `devapi`，**本套件不含那两个库**。
>
> 为什么仍保留那 4 条：它们的价值不在「哪个库错了」，而在**抓住机制**——
> 「装置的失败被当成被测对象的失败」这条教训对任何做实验的人都适用。
> 已在各条开头标注所属资产是否在本套件内。

## 一、V4 已推翻（2 条）

这两条曾被我当成结论写进过文档，后来被**复现检查**推翻。

### 1. `capturetrap-nav` · `am start` 是恢复原语

| | |
|---|---|
| **原始观测** | 不 force-stop 时三种 `am start` 命令全部落错；force-stop 后全部落对。看起来非常干净 |
| **为什么危险** | 有对照组、规律清晰，是最像「发现」的一类 |
| **怎么推翻的** | 换起始状态重跑 → 不 force-stop 也三次全部正确落地 |
| **根因** | 把「复位」这个**装置行为**当成了「被测对象」的行为 |
| **教训** | **复位本身也要有判据。** 否则装置的失败会被当成被测对象的失败 |

同源问题在 `swipefind` 的 `reset_home()` 上又犯过一次（`am start` + `BACK`
不重置滚动位置），导致「200ms 以下完全无效」这个错误结论。

### 2. `swipefind-200ms` · 「200ms 以下完全无效」

| | |
|---|---|
| **原始观测** | 6 次固定距离手势，200ms 全部无滚动 |
| **为什么危险** | 阈值清晰、可量化，很适合写进规范 |
| **怎么推翻的** | 改用 HOME 键复位后重跑 → 200ms **有效** |
| **根因** | 复位不干净 → 每次手势的起始滚动位置不同 → 阈值假象 |
| **教训** | 与上条同源：**装置的失败被当成了被测对象的失败** |

## 二、V0 单次观测（4 条）

这四条不是「错」，是「**证据不够**」。按 `claimcheck` 规则：
单次观测只能产生假设，不能产生结论。

### 3. `agentloop-e2e` ⚠️ *资产不在本套件* · S1/S2 四场景指标值

- **性质**：指标值设备相关，且未固化输入
- **处置**：已固化 `data/scenarios/`（5 份 XML + manifest），
  指标仍由 agentloop 自己跑——**只固化输入，不固化输出**
- **能承诺的**：结论（S1/S2 无失效事件时两种设计等价）
- **不能承诺的**：steps / clicks / wasted 的具体数值

### 4. `agentloop-s3` ⚠️ *资产不在本套件* · S3 慢一拍下引用派点错了

- **性质**：设备相关单次观测
- **但有回归测试**：`test_stale_ref_reassigned_silently_misdirects`
  钉住「`StaleRefError` 抓不住引用被重新指派」
- **注意区分**：测试是针对**方案**的，不是针对**数值**的

### 5. `devapi-e2e` ⚠️ *资产不在本套件* · 真机全链路跑通（9 端点）

- **性质**：设备相关单次观测
- **已固化的**：契约层 12 份 fixtures（字段名/类型/状态码），离线可复算
- **★ 最需要说清的一点**：验收剧本里的「外部 agent」是
  **概念验证**——由本项目自己跑通，**不是第三方独立复现**
- **能承诺的**：契约形状稳定、端点行为可复算
- **不能承诺的**：换设备/换环境仍跑通

### 6. `capturetrap-stale` · 原地覆写：连续 5 次 dump+cat md5 全部相同

- **性质**：**5 次观测，但存在未排除的替代解释**（屏幕可能真的没变）
- **为什么仍是 V0**：`claimcheck` 的核心规则是「观测次数」与
  「替代解释是否排除」是两个独立维度。**观测多次不等于可引用**
- **能承诺的**：这个陷阱存在且会静默发生
- **不能承诺的**：「连续 5 次都相同」这个具体数字

### 7. `prop04-crisp` · 带 `since` 409 / 删掉 `since` 200 的 crisp 对照

- **性质**：设备相关单次对照
- **★ 这条是我自己刚写完规则就犯的**：提案 04 里我手写成 V1，
  `classify()` 复算立刻抓回 V0——`observations=1` 就是 V0，
  与起始状态数、通道数无关
- **能承诺的**：结论「删掉安全字段会 fail-open」
- **不能承诺的**：409 / 200 这两个具体状态码数值

## 三、这 7 条教的三件事

**① 「观测多次」不等于「可引用」。**
`capturetrap-stale` 有 5 次观测仍是 V0，因为替代解释没排除。
观测次数和替代解释是**两个独立维度**。

**② 装置的失败会被当成被测对象的失败。**
两条 V4 都是这个根因（`am start` 复位、`reset_home()` 复位）。
**复位本身也要有判据**——这是本次最贵的一条教训，
直接产生了 `agentloop` 对照实验里「必须断言自变量真的被改变了」那条规定。

**③ 写文档这个动作本身就会触发过度声称。**
`prop04-crisp` 是刚立完规则、同一天写提案时就犯的。

> **共同根因只有一个：写文档时自带乐观偏差。**
> 对策不是「更小心」，是 `claimcheck` / `claimaudit` 这**两层可执行的检查**
> ——不是文档纪律，是跑得起来的代码。
