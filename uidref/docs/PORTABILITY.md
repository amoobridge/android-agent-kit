# 规范可移植性验证方法

**uidref 附带文档 · License Apache-2.0 · v0.1**

---

## 摘要

一份规范加上一批黄金向量、一个参考实现、一个全绿的测试报告——
这套东西看起来完整，实际上**可能一条都没验证到规范本身**。

本文用一个真实案例说明这件事怎么发生、怎么发现、怎么防：

> uidref 规范的黄金向量曾达到 **34/34 全绿**，但其中 **12 条用例一条都没测到它声称的规则**。
> 让它们失效的是向量**生成器**的两个 bug，而不是规范或实现。
> 发现方式不是更仔细地读代码，而是**用第二种语言独立实现了一遍规范**。

案例之外，本文给出三层可复用的验证法，以及一份**规范歧义分类学**——
按它自查，能在规范定稿前拦住绝大多数跨语言分叉。

---

## 1. 问题：黄金向量全绿 ≠ 规范可移植

### 1.1 常见的错误假设

> "我有 N 条黄金向量，参考实现全过，所以规范是明确的、任何人都能实现出一致的结果。"

这个推理有两处断裂：

1. **向量可能没测到它声称的东西**（vacuous vector）
2. **向量只覆盖了作者想到的输入**，而规范歧义恰恰藏在作者没想到的地方

### 1.2 案例：34/34 全绿，12 条空转

uidref 规范的向量生成器有两个 bug。

**Bug 1：属性名泄漏。**

生成器的节点构造函数接受关键字参数，并**把参数名直接当成 XML 属性名**。
规范需要 `class` 与 `resource-id` 两个属性，但 `class` 在 Python 里是关键字，
所以调用点改用了短名 `cls=` / `desc=` / `rid=`。这些名字于是**泄漏成字面 XML 属性**，
而真正的 `class=` / `resource-id=` 仍是默认值。

后果——角色推断的 8 条用例**全部在跑同一个类**：

| 用例声称 | XML 里实际是什么 | 实际产出 |
|---|---|---|
| `Button → btn` | `cls="android.widget.Button"` + `class="android.view.View"` | `item` |
| `EditText → input` | 同上 | **0 个元素**（`View` 不算可交互） |
| `SeekBar → slider` | 同上 | **0 个元素** |

向量仍然"通过"，因为**期望值是用同一份坏 XML 生成的**。生成器与实现共享了同一个盲区。

**Bug 2：自闭合节点。**

构造函数恒返回自闭合标签 `<node .../>`，容器拼接只做字符串相加。
于是所谓"子孙文本继承"的 4 条用例里，子节点其实是**兄弟节点**。
4 条用例的期望标签**全是空字符串**。

### 1.3 为什么这种失效能活很久

三个原因叠加：

1. **期望值由实现自身生成**，不是手写。生成器烂，期望值就烂，比较仍然相等。
2. **同一作者、同一语言、同一心智模型**写生成器和实现。盲区是共享的。
3. **没有元测试**问"这条用例真的在测东西吗"。

第 2 点是最根本的：**只要生成器与实现同源，它们就会一起错，而且错得一致。**

## 2. 三层验证法

### L1 独立跨语言实现

**做法**：找第二种语言，**照规范正文重新实现一遍**，不是翻译第一份实现。

**为什么有效**：翻译会继承原实现的全部隐含假设；独立实现强迫你**读规范**而不是读代码。
上例中，JS 实现写到角色推断时，第一件事是去 XML 里找 `class` 属性——
于是立刻发现 XML 里根本没有它。

**成本**：一份实现的工作量。**收益**：这是唯一能打破"同源盲区"的手段。

**要点**：
- 必须**从规范正文出发**。允许读规范、不允许读第一份实现的源码。
- 语言要**语义不同**。Python → JavaScript 能抓出取整、属性遍历、字符串编码差异；
  Python → Ruby 收益小得多。
- 两边跑**同一批向量**，再在**真实数据**上逐字段比对。

### L2 变异敏感性（防空转）

**做法**：对每条用例的输入做小改动，**断言输出必须变化**。若输出不变，该用例是空转。

```python
# 伪代码
base = impl(xml)
mutations = [
    xml.replace('clickable="true"', 'clickable="false"'),
    xml.replace('enabled="true"', 'enabled="false"'),
    re.sub(r'text="[^"]*"', 'text="变异"', xml, count=1),
    re.sub(r'bounds="[^"]*"', 'bounds="[9,9][99,99]"', xml, count=1),
    # ...
]
assert any(impl(m) != base for m in mutations if m != xml)
```

**为什么有效**：它不针对任何具体 bug。不管向量为什么失效，
**只要它的输出是常数，就说明这条输入没走到它声称的规则上。**

这是**通用防线**——上面那条属性名泄漏的 bug，会被这一条测试直接抓住：
改 `class` 属性名不影响输出，因为输出压根不读它。

**边界**：空输入、纯错误路径无法变异，需豁免。

### L3 随机差分

**做法**：随机生成合法输入，同时喂两个实现，比对结构化输出。

**为什么有效**：黄金向量是**人工挑的**，真实数据是**现实形态的**，两者都通过
只能说明"在已知输入上一致"。规范的价值在于**任何人任何语言实现都同结果**——
那需要随机输入上的证据。

**成本**：一个生成器 + 一个比对器。**收益**：把"我们测过"变成"我们测了很多"。

**⚠️ 生成器自身必须先验证**。本案例中，差分测试头两次跑出 247/300 "分歧"，
差点被当成规范歧义上报。实际是生成器自己的 bug：

1. `"".join(attrs)` 少了空格，生成的**全是非法 XML**
2. 属性值含裸 `"` 与 `<` **未转义**

修好后 300 条随机输入两侧才真的一致。

> **教训：差分测试的生成器，本身要先验证它在生成合法输入。**
> 判别方法：让一个**严格的**解析器（如 Python `xml.etree`）先过一遍，
> 它报错的输入就是生成器的 bug，不是规范的分歧。

## 3. 规范歧义分类学

跨语言独立实现是规范歧义的**探测器**。下列五类是本次实际撞出来的，
按"规范写错了什么"归类，可直接用于自查。

### T1 宿主语言记法借用

| | |
|---|---|
| **症状** | 规范用了某种编程语言的运算符或语法 |
| **本例** | 中心点写成 `((x1+x2)//2, (y1+y2)//2)` |
| **为何分叉** | Python 的 `//` 向负无穷取整；JavaScript 的 `\|0` 与 `>>1` 向零截断。规范又允许负坐标 → **差 1** |
| **检测** | L1。换一个取整语义不同的语言立即暴露 |
| **修法** | 用文字写语义：「必须 floor（向负无穷取整），不是向零截断」 |

**通则**：规范里出现 `//`、`%`、`&`、`|`、切片语法、`NaN` 之类，一律改为文字描述。

### T2 开口枚举

| | |
|---|---|
| **症状** | 列举若干项后加「等」「之类」 |
| **本例** | 「`content` / `container` / `root` … **等**结构性容器名」 |
| **为何分叉** | 各实现自行扩充集合。集合不同 → 标签不同 → 同一输入两种输出，破坏规范的确定性条款 |
| **检测** | L3。随机 resource-id 会撞到扩充边界 |
| **修法** | 给**穷举集合**，并写明「实现不得自行扩充」 |

**通则**：规范要的是可判定性，不是表达力。「等」字一出现，就必须问：谁来定这个集合？

### T3 输入域未定义

| | |
|---|---|
| **症状** | 规范说输入是"某工具的输出"，但不定义其边界 |
| **本例** | 只说输入是 `uiautomator dump`，未说实体转义、CDATA、注释、命名空间、畸形输入 |
| **为何分叉** | 严格解析器对未转义引号**报错**，宽松解析器**接受**。两者都"符合规范" |
| **检测** | L1 + L3 |
| **修法** | 加一节「输入子集」：明确实现必须支持什么、可以容忍什么、**规范对什么不约束** |

**通则**：把"我不关心的"明确写成"不约束"，而不是留空。留空会被读成"随便"，
而"随便"在跨语言时就是分叉。

### T4 确定性不足

| | |
|---|---|
| **症状** | 规范只说"结果必须确定"，不说**按什么顺序** |
| **本例** | 「同一份 XML 必须产生同一组 ref」——没说编号顺序 |
| **为何分叉** | 按文档序编号、按 bounds 排序、按 y 坐标分组，**三者都"确定"**，但 ref 不同 |
| **检测** | L1。第二个实现几乎必然选另一种顺序 |
| **修法** | 明确「按前序深度优先文档序，从 `e1` 起连续递增」 |

**通则**：**"确定"是性质，不是规格。** 必须给出产生顺序的构造性描述。

### T5 默认值与可选行为欠规定

| | |
|---|---|
| **症状** | 规则写了主干，分支条件用「建议」或干脆没提 |
| **本例** | 「拼接必须有上限（**建议** 4 段）」；未说继承是否含 `content-desc`、是否跨代 |
| **为何分叉** | 建议不是约束。含不含 desc、跨不跨代、上限 4 还是 5，四个维度各自分叉 |
| **检测** | L1 + L3 |
| **修法** | 该升必须的升必须；未提的分支全部补上，包括分隔符这种细节 |

**通则**：**"建议"在规范里是噪声。** 要么写成"必须"，要么明确写成"可以"。

### 附：覆盖盲区（不是规范歧义，但同源）

| | |
|---|---|
| **症状** | 规范的某条规则**根本没有向量覆盖** |
| **本例** | §5 的 center 取整规则写了，但向量只比对 `bounds` 原值，不比对 center |
| **后果** | 拿一个**向零截断**的实现来测一致性，**竟然全绿**——一致性测试对一个真实分歧完全失明 |
| **检测** | L3（随机差分）也救不了，因为两边都没输出 center。要靠**审契约字段 vs 规范条文** |
| **修法** | 凡是规范里必须的**导出值**，都必须进比对契约。补两条负奇数用例后，截断实现立刻被抓到 |

> 这一条最阴险——它不属于上面五类中的任何一类，因为规范写得没错，
> **错在验证契约漏了字段**。定稿前应逐条核对：规范的每个必须，在契约里有对应字段吗？

## 4. 如何验证你自己的实现

uidref 提供语言无关的一致性工具。**不管你的实现用什么语言**，
只要提供一个「XML 进、JSON 出」的命令即可。

### 契约

```bash
$ <你的命令> <input.xml> > output.json
```

```json
{
  "package": "com.example",
  "rotation": 0,
  "elements": [
    {
      "ref": "e1", "role": "item", "label": "OK",
      "bounds": [0, 0, 100, 100],
      "center": [50, 50],
      "clickable": true, "long_clickable": false, "scrollable": false,
      "editable": false, "checked": false, "disabled": false, "password": false
    }
  ]
}
```

- `bounds` 是 `[x1, y1, x2, y2]`，半开区间
- `center` 是真正被 tap 的点：`floor((x1+x2)/2)`、`floor((y1+y2)/2)`。
  **必须向负无穷取整**，不是向零截断
- `ref` 从 `e1` 起按前序深度优先文档序连续编号
- 布尔一律 JSON `true`/`false`，不是 `"true"` 字符串
- **全部字段必须存在**，缺一个就算不符

### 用法

```bash
# Node 实现
python tools/verify_impl.py vectors/ --cmd "node js/impl.js"

# Rust 实现（先编译）
python tools/verify_impl.py vectors/ --cmd "./target/release/uidref"

# 单条调试
python tools/verify_impl.py vectors/ --cmd "node x.js" --case robustness-001:4
```

退出码 `0` = 全部通过；`1` = 有不符；`2` = 用法/环境错误。

`../js/impl.js` 是一个**最小包装范例**——实现核心逻辑在 `../js/uidref.js`，
`../js/impl.js` 只做「文件参数 → stdout」的适配。任何语言照这个形状包一层即可。

## 5. 证据

### 三层验证结果

| 层 | 内容 | 结果 |
|---|---|---|
| L1 | 45 条黄金向量，Python 与 JS 两个独立实现同跑 | Python 45/45 · JS 45/45 |
| L1 | 16 个真实 dump 逐字段比对 | **完全一致** |
| L3 | 随机差分，5 个 seed × 200 条 | **0 分歧** |

### 反向验证（工具必须能抓到坏实现）

| 破坏形态 | 检出 |
|---|---|
| 布尔写成字符串 `"true"` | ✅ 39/45 失败，报「应为布尔」 |
| 缺 `password` 字段 | ✅ 39/45 失败，报「缺字段」 |
| 缺 `center` 字段 | ✅ 39/45 失败，报「缺字段」 |
| center 向零截断（A1 真实分歧） | ✅ **精确 2/45 失败**——正是两条 A1 判定用例 |

最后一条值得说明：补了负奇数 bounds 用例后，截断实现**只失败那两条**。
这说明向量是**精准的**，不是靠大面积误报覆盖。

### 元测试

`tests/test_uidref.py::TestVectorsNotVacuous` 提供五条元测试，
其中变异敏感性是通用防线。已做反向验证：把旧 bug 形态的向量塞回去，
4 条元测试立即报警。

## 6. 局限

诚实列出这套方法**不能**保证什么：

1. **L1 只覆盖两种语言。** 第三种语言可能撞出第六类歧义。语言差异越大，探测器越灵。
2. **L3 只覆盖生成器能生成的输入分布。** 生成器想不到的形态（超深嵌套、异常编码、
   超大 bounds）仍然不在覆盖内。
3. **变异集合是手写的。** 没变异到的属性，空转用例仍可能漏网。
   本例中 `class` 属性一开始就不在变异集合里——抓到它靠的是 L1，不是 L2。
4. **规范可能本身有错，只是两个实现错得一致。** 两个实现同源于同一份规范正文，
   规范写错时它们会一致地错。此时需要**第三方的真实数据**做裁判——
   这就是为什么 16 个真实 dump 的比对不可省。
5. **本文的分类学来自单一案例。** 五类是这次撞见的，不是完备的。

## 7. 给规范作者的自查清单

定稿前逐条过：

- [ ] 规范里有没有 `//` `%` `&` `\|` 之类**宿主语言记法**？全部改成文字（T1）
- [ ] 枚举项后面有没有「**等**」「之类」？改成穷举 + 不得扩充（T2）
- [ ] 输入域写清楚了吗？包括**明确不约束什么**（T3）
- [ ] 每个"必须确定"的地方，都给了**构造性顺序**吗（T4）
- [ ] 还有没有「**建议**」级别的约束？该升必须的升（T5）
- [ ] 规范里每个必须的**导出值**，在比对契约里都有字段吗（覆盖盲区）
- [ ] 黄金向量的期望值是**手写的**还是**实现生成的**？后者必须配元测试
- [ ] 有**变异敏感性**元测试吗
- [ ] 有**第二种语言的独立实现**吗
- [ ] 有**随机差分**吗？生成器本身验证过在生成合法输入吗
- [ ] 有**真实数据**做第三方裁判吗
